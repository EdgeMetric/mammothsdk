## Matrix workflow grouping

The release matrix separates CLI core workflows from miscellaneous APIs as an
inventory lens, not a support claim: **230 Core** and **298 Miscellaneous**
operations. Core workflow families are `project`, `context`, `dataset`, `file`,
`folder`, `view`, `job`, `export`, and `pipeline`, plus dashboard primary
workflows, trash/recovery, and adjacent settings/data surfaces. Public,
rendered, asset-delivery, and other peripheral APIs are miscellaneous. Each
row retains its own status, evidence, authorization, and semantic-proof
boundary. The grouping does not imply parity or readiness.
The workbook source-of-truth is `CORE-CAPABILITY-GROUPING.json`; dataset/view/
pipeline/task/export CRUD is Core regardless of HTTP method. Dashboard analytics,
heartbeat/view tracking, telemetry, public/rendered/asset delivery routes are
Miscellaneous; primary dashboard CRUD remains Core.

## Proof boundary

A row is not a pass merely because it has a handler, an agent example, or a test identifier. The ledger records the acceptance class from the reviewed command map. Independent execution, expected-state oracles, backend authorization, display-name resolution, recovery and cleanup remain separate fields.

For every capability, the agent-facing column policy is display names only. The row says `not_certified` until the adapter resolves local/foreign names and independently proves missing/ambiguous-name behavior before mutation.

## Explicit gaps and backend limits

- The ledger classifies all 53 SDK methods without canonical commands. 0 have missing dedicated CLI alias targets; the rest are duplicate surfaces, helpers, or backend-blocked seams.
- Protocol-only operations (health, provider callbacks, telemetry, OAuth callback and unsubscribe) remain in `api_inventory`. They are not user capabilities.
- The ledger carries known `BLOCKED[...]` restrictions and blocked upload/permission cases row-by-row. A route does not make a blocked row available.
- Resource identity, postcondition readback, uncertain-write reconciliation, dependency-aware cleanup and pagination progress are not independently certified by this artifact.

## Source conflicts and authority

The pinned OpenAPI metadata and generated operation manifest agree at 445 operations and 287 paths. The historical `spec/reports/parity.md` says 376 operations and 234 paths with a different hash. We retain it as a conflict and exclude it from counts. The generated SDK manifest says 549 methods. The source catalog says 541 and the historical report says 242. We use the generated introspection manifest. It classifies every non-canonical method and exposes 0 missing dedicated routes. The review ledger reports 268 files pending exhaustive semantic review and 34 targeted-only.

Authority and hashes are in the `sources` and `source_conflicts` fields of the JSON ledger. The conflict rule is to prefer the hash-matching pinned/generated source and preserve every disagreement instead of silently merging it.
